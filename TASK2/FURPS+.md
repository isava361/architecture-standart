| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | Сайт: Клиент может просмотреть список доступных депозитов с актуальными ставками|Архитектурно-значимое: Требуется интеграция с системой, хранящей актуальные ставки|
| F2  | Сайт: Новый клиент может подать заявку на депозит, указав ФИО и номер телефона.|Архитектурно-значимое: Требуется интеграция с системой кол-центра для обработки заявки|
| F3  | Интернет-банк: Клиент может видеть список доступных депозитов с общими и персональными ставками|Архитектурно-значимое: Требуется система расчета и хранения персональных ставок и ее интеграция с интернет-банком|
| F4  | Интернет-банк: Клиент может подать заявку на открытие депозита, выбрав счет и указав сумму|Это ключевая функция MVP|
| F5  | Интернет-банк: Клиент должен подтверждать операцию подачи заявки на депозит через СМС-код|Архитектурно-значимое: Требуется интеграция с СМС-шлюзом|
| F6  | Бэк-офис: Сотрудники бэк-офиса (депозитного и кредитного отделов) должны иметь возможность управлять ставками по депозитам в единой системе|Архитектурно-значимое: Необходимо создать новый модуль (вероятно, в АБС) или отдельную систему для управления ставками, заменяющую Excel-файлы|
| F7  | Бэк-офис: Сотрудник бэк-офиса обрабатывает и подтверждает заявку на депозит, поступившую из онлайн-каналов, в АБС|Это основной процесс на этапе MVP|
| F8  | Система: После подтверждения заявки бэк-офисом система автоматически отправляет клиенту СМС-уведомление|Требуется автоматизация процесса уведомления|
| F9  | Кол-центр: Менеджер кол-центра получает заявки с сайта в своей системе и связывается с клиентом|Требуется доработка системы кол-центра для приема и обработки нового типа заявок|
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейсы сайта и интернет-банка должны соответствовать принятой в компании системе дизайна (брендированные элементы, цвета)|Обеспечивает узнаваемость бренда и целостность пользовательского опыта|
| U2  | Интерфейс для сотрудников бэк-офиса по управлению ставками должен быть интуитивно понятным, чтобы заменить текущую работу в Excel |Снижает сопротивление изменениям и затраты на обучение персонала|
| U3  | Процесс подачи заявки на депозит в онлайн-каналах должен быть простым и требовать минимального количества шагов от клиента |Важно для привлечения и удержания новых, более молодых категорий клиентов|
| R   | Надёжность (Reliability)           |              |
| R1  | Все новые сервисы (включая интернет-банк) должны быть доступны 24/7 с показателем доступности 99,9%|Архитектурно-значимое: Критическое требование для банковских онлайн-сервисов|
| R2  | Необходимо обеспечить отказоустойчивость интернет-банка за счет резервного ЦОД|Архитектурно-значимое: Текущая реализация переключения на резервный ЦОД не удовлетворяет требованиям доступности|
| R3  | Данные клиента, передаваемые с сайта и из интернет-банка, должны быть защищены механизмами шифрования трафика (например, HTTPS/TLS)|Архитектурно-значимое: Обязательное требование при работе с персональными и финансовыми данными|
| P   | Производительность (Performance)   |              |
| P1  | Отклик интерфейсов сайта и интернет-банка на действия пользователя должен занимать 100 ms |Архитектурно-значимое: Влияет на удовлетворенность клиентов. Требует оптимизации, возможно, кэширования|
| P2  | Система должна выдерживать нагрузку от онлайн-подачи заявок на большое количество продуктов в будущем (1000 RPS)|Архитектурно-значимое: Требуется проектирование масштабируемой архитектуры|
| P3  | Необходимо предусмотреть равномерное горизонтальное масштабирование и распределение запросов для компонентов интернет-банка|Архитектурно-значимое: Обеспечивает производительность и надежность при росте нагрузки|
| P4  | Загрузка справочных данных в интернет-банке должна быть оптимизирована (не более секунды)|Улучшение текущей производительности для повышения лояльности клиентов|
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Необходимо разработать документацию для дальнейшего расширения и поддержки системы |Важно для снижения зависимости от конкретных разработчиков и упрощения будущих доработок|
| S2  | Новые компоненты должны быть совместимы с существующими платформами разработки (.NET, Java)|Снижает порог входа для существующих команд разработки|
| S3  | Реализация бизнес-функционала (например, отправка СМС) должна выполняться силами команды банка, чтобы избежать зависимости от подрядчика интернет-банка|Повышает гибкость и скорость внесения изменений в будущем|
| S4  | По возможности, рассмотреть перевод части функционала интернет-банка на микросервисную архитектуру|Архитектурно-значимое: Упростит независимую разработку, развертывание и масштабирование отдельных функций|
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Максимально использовать существующий в банке технологический стек (MS SQL, Oracle, .NET, Java, PHP, React.js)|Снижает затраты на лицензирование нового ПО и обучение персонала|
| +R2 | При необходимости внедрения очередей сообщений использовать Kafka|Стратегическое технологическое решение с учетом будущих потребностей|
| +R3 | Текущая версия платформы интернет-банка (.NET Framework 4.5) несовместима с Kafka|Архитектурно-значимое: Это ограничение потребует либо обновления платформы, либо поиска альтернативных решений для интеграции на этапе MVP|
| +R4 | АБС может масштабироваться только вертикально|Архитектурно-значимое: Важное ограничение, влияющее на проектирование интеграции и общую производительность системы|
| +R5 | Сотрудники депозитного и кредитного отделов не должны иметь прямого доступа к данным друг друга в АБС по требованиям безопасности|Архитектурно-значимое: Требует реализации разграничения прав доступа в новой системе управления ставками|
| +R6 | На этапе MVP обработка заявок продолжает осуществляться сотрудниками бэк-офиса вручную|Определяет рамки и сложность первой версии продукта|
| +R7 | Новые клиенты с сайта должны проходить личную идентификацию в отделении банка (KYC)|Законодательное ограничение, которое влияет на клиентский путь|
| +R8 | Прямая интеграция интернет-банка с базой данных АБС должна быть исключена в новом процессе|Архитектурно-значимое: Снижает риски нарушения стабильности и безопасности основной банковской системы|
